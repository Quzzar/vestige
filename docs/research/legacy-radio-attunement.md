# Legacy Sending Shell and Attunement Shard inspiration

**Status:** primary-source research, checked October 4, 2026. This records the owner's archived plugin and design inferences for a future native Attunement Shard. It does not authorize a legacy-system port, prescribe the new shard's recipe, or implement communication or teleportation.

**Source:** [Quzzar/Minecraft-Plugins](https://github.com/Quzzar/Minecraft-Plugins), `RPChat`, pinned to [commit `ae6b044df426fdda96bb643822c85e815cf88a8e`](https://github.com/Quzzar/Minecraft-Plugins/commit/ae6b044df426fdda96bb643822c85e815cf88a8e), whose recorded commit date is January 18, 2024. The plugin identifies itself as RPChat 1.0, targeting Bukkit API 1.14 in its [plugin descriptor](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/plugin.yml).

## What the old plugin actually does

The magical radio is called a **Sending Shell**. Its item is a named, enchanted nautilus shell. Its registered **shapeless** recipe contains two iron ingots, one redstone, one note block, and one nautilus shell. The source registers this fixed ingredient set rather than accepting arbitrary ingredients. [Recipe and item construction](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioCreator.java#L66-L87).

Although every valid arrangement can craft the item, **the channel identity is positional**. `serializeMatrix` visits the crafting matrix in its supplied array order, writes the first letter of each occupied slot's `Material.name()`, and writes `~` for an empty slot. It does not sort the inputs. It does not read stack amount, durability, enchantments, names, lore, or other item metadata. [Matrix serialization](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L55-L68).

For example, arranging the five ingredients in the first five positions can produce `IIRNN~~~~`. Moving the redstone to a previously empty position changes the string and therefore requests a different channel. Swapping the note block and nautilus shell preserves the string because both encode as `N`. These examples are direct deductions from the [serializer](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L55-L68) and the [fixed ingredient list](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioCreator.java#L79-L84).

The crafting listener passes the complete matrix to the channel-registration function. It allows the `PICKUP_ALL` inventory action and cancels other actions when crafting a Sending Shell. A separate handler prevents Sending Shells from being used as crafting ingredients. [Crafting handlers](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioListener.java).

## Identity, display, persistence, and use

The channel is not a numerical frequency or a deterministic hash. `makeRegisteredRadio` looks up the serialized matrix in the server's `RadioManager`. If the string already exists, it reuses that `Radio`; otherwise it creates one. Each newly created `Radio` stores the matrix string and chooses a **random colored glyph prefix** from the plugin's character list and Bukkit's `ChatColor` values. The crafted item's lore stores that prefix after a frequency label. [Registration and prefix generation](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L44-L86), [Radio model](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/Radio.java), [character list](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/misc/CodeSet.java).

The registry is Java-serialized to `Data/radio_channels.data`, restored when constructing `RadioManager`, and saved from the plugin's disable callback. A Sending Shell is identified by matching its item template while ignoring lore; its first lore line then supplies the prefix used to resolve the corresponding registry entry. Consequently, the same recipe reproduces the same displayed frequency **while that registry is retained**. Rebuilding the registry can assign a different random prefix to that matrix; existing items do not contain their matrix string. [Registry load/save and lookups](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioManager.java), [disable callback](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/RPChat.java#L80-L85), [item lookup](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L89-L100).

Only Sending Shells in the player's nine hotbar slots participate. Normal chat from a player carrying one goes to online players with a common resolved `Radio`, rather than through local chat. The radio path does not check distance or world; a player can carry several channels and communicate with recipients sharing any of them. The common-channel test intersects lists of registry objects, and `Radio` does not override equality. [Hotbar scan](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L21-L41), [chat routing](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/ChatListener.java), [Radio model](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/Radio.java).

## Limits evident in the source

These are source-level deductions, not observed failures from running the archived plugin:

- **Material abbreviation loses identity.** `NOTE_BLOCK` and `NAUTILUS_SHELL` collide as `N` in the actual recipe. Other materials with a shared initial would also collide if the input set were expanded. [Serializer](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L55-L68).
- **Random display prefixes can alias distinct channels.** Channel creation does not check whether the randomly generated prefix is already in use. Item lookup returns the first registry entry with a matching prefix, so a collision can resolve an item to another matrix's channel. [Prefix generation](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L44-L52), [creation and prefix lookup](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioManager.java#L53-L82).
- **Presentation is also the lookup key.** The item stores a styled lore prefix rather than the complete identity. `getRadioFromItem` directly accesses the first lore line after template matching; missing lore is not guarded at that point. [Item lookup](https://github.com/Quzzar/Minecraft-Plugins/blob/ae6b044df426fdda96bb643822c85e815cf88a8e/RPChat/src/com/quzzar/rpchat/radio/RadioUtilities.java#L89-L100).

## Inferences for native Attunement Shards

The following are recommendations derived from this research and the owner's current concept, rather than behavior of RPChat or accepted implementation details:

1. **Keep recipe eligibility and signal identity separate.** The old plugin demonstrates that shapeless recipe acceptance can coexist with a positional fingerprint. Decide explicitly whether a new shard's offering positions matter. If the shard is fully shapeless for identity, serialize a sorted multiset of consumed ingredient identities and counts. If offering-to-Plinth or offering-to-imbuement pairings matter, record those associations and describe the rule to the player.
2. **Use complete identities.** Namespaced item and embedded-material identifiers preserve distinctions lost by single-letter encoding. Only selected meaningful item components should participate; incidental names, remaining stack size, or unrelated metadata should not silently retune a shard.
3. **Derive the signal deterministically from canonical inputs.** Include the selected active leyline geometry and positioned imbuements, rather than random channel allocation or final rounded spell bonuses. Normalize only the transformations the owner intends to preserve. Keep fingerprint format/version independent of geometry balance coefficients.
4. **Store the actual key in native item data.** A rune, color, short code, or player label can describe it, while device matching compares the complete stored key. A registry may later track installed devices or destinations; it need not be required merely to reproduce an attunement.
5. **Reuse attunement across independently authored devices.** Communication, teleportation, and other recipes can consume or inherit a shard's key. Matching identity establishes a channel; range, targeting, destination selection, permissions, and costs remain decisions for each device's behavior.

The inherited precedent worth preserving is that players can **reproduce a connection by reproducing a craft**, and can invent another connection by changing its inputs. The new design should deliberately choose which relationships form the signal, instead of inheriting the archived plugin's abbreviation, registry, and lore dependencies. No legacy code or assets were copied into Vestige by this research.
